# ADR: Pick a host and reserve the placement in one transaction

Related: [issue #137](https://github.com/liquidmetal-dev/battery/issues/137),
[issue #18](https://github.com/liquidmetal-dev/battery/issues/18).
Changes how `Provision` uses the placement reservations from
[the host API ADR](2026-09-24-host-api.md).

- Status: Accepted
- Date: 2026-11-16

## Context

When a pool is short of VMs, `provisionN` starts one goroutine per missing
VM, and each goroutine runs `Provision`. Until now, `Provision` took three
steps:

1. `ineligibleHosts` listed the cordoned and unregistered hosts.
2. `PickHost` counted the pool's VM records on each other host, and took
   the host with the fewest. A tie went to the first host in
   `FlintlockHosts`.
3. `ReservePlacement` recorded the placement, after a check that the host
   was still registered and not cordoned.

The VM record appears only after `CreateMicroVM` returns. `PickHost` did
not count placements. So every goroutine of a batch read the same counts
in step 2, and picked the same host. With equal counts, a whole batch went
to the first host in the list.

We saw this on v0.3.3 with two hosts. Two pools resized from 1 to 8 put all
16 VMs on one host. The first batch of each pool failed with
`Unavailable` errors from that one flintlockd. A pool spread out only as
its VMs were claimed and replaced one at a time.

## Decision

Add `Store.PlaceVM`. It picks the host and reserves the placement in one
transaction:

```go
PlaceVM(ctx context.Context, id, poolName, poolNamespace string, hosts []string) (string, error)
```

In one transaction on the store's single connection, `PlaceVM`:

1. Reads the hosts that are registered and not cordoned.
2. For each of those hosts in `hosts`, counts the pool's VM records in any
   phase but `DELETING` and `FAILED`, plus the pool's placements on it.
3. Picks the host with the lowest count. A tie goes to the host that comes
   first in `hosts`.
4. Inserts the placement, and returns the host.

If no host in `hosts` is eligible, it returns `store.ErrNoEligibleHost` and
records nothing. `Provision` wraps that in `reconciler.ErrNoEligibleHost`,
so `provisionN` still logs it quietly.

`Provision` calls `PlaceVM` in place of the three steps. `PickHost` and
`ineligibleHosts` are removed. The rest of the placement's life does not
change: `ReleasePlacement` removes it when the VM record exists or the
provision fails, and `ClearPlacements` removes all of them at startup.

### Why this spreads a batch

The store has one connection (`SetMaxOpenConns(1)`), so its transactions
run one at a time. The goroutines of a batch call `PlaceVM` in some order.
Each call counts the placements of the calls before it. A batch of 8 on two
empty hosts gets 4 on each. A batch of 4 on hosts with 1 and 3 VMs gets 3
on the first and 1 on the second.

### Cordon and remove

The cordon and registry checks are in the transaction that reserves the
placement, as in `ReservePlacement`. `SetHostCordoned` and `DeleteHost`
either commit first, and the host is not picked, or see the placement
counted. The window between the pick and the reservation, where a cordon
could land, is gone.

## Consequences

Positive:

- A batch spreads across the hosts by count, as single replacements
  already did. A batch no longer sends all its creates to one flintlockd.
- A retry after a failed batch is spread too, because a failed create
  releases its placement.
- The pick and the cordon check can no longer disagree, so `Provision` has
  one error path for "no host" in place of two.

Negative:

- The `Store` interface gains a method, and the placement logic moves from
  the reconciler into the store.
- Each `PlaceVM` holds the store's connection for two reads and an insert.
  `PickHost` and `ReservePlacement` together did the same work in separate
  calls, so the total cost is about the same.

## Alternatives considered

- **Assign the hosts for the whole batch in `provisionN`.** It reads the
  counts once, and gives each goroutine its host. It is smaller, but it
  sees only its own batch. It also leaves the pick and the reservation
  apart, with the cordon window between them.
- **Break ties at random.** A few lines, but a batch is spread only on
  average, and a batch on uneven hosts still goes to the least loaded one.
- **Count placements in `PickHost`, and keep `ReservePlacement` apart.**
  Two goroutines can still read the same counts before either reserves.

## Out of scope

- Placement by host resources, such as CPU and memory (#18). `PlaceVM`
  still spreads by the pool's VM count only.
- Counting other pools' VMs on a host. As before, each pool spreads its own
  VMs. [The memory ADR](2026-11-17-place-vm-by-memory.md) later changed
  this.
