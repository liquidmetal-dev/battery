# ADR: A Host API for dynamic inventory

Related: [issue #97](https://github.com/liquidmetal-dev/battery/issues/97).
Extends the host registry that [PR #83](https://github.com/liquidmetal-dev/battery/pull/83)
added for [issue #66](https://github.com/liquidmetal-dev/battery/issues/66).

- Status: Accepted
- Date: 2026-09-24

## Context

The pool manager learns about flintlock hosts from one place: the `hosts`
list in its JSON config file. Each entry has a name, a gRPC address, and TLS
material. `config.Load` reads the list once, at startup. `flintlockclient.New`
then dials every host and stores the connections in plain maps. Nothing can
change those maps while the process runs.

This has three effects an operator feels:

- To add or remove a host, the operator edits the file and restarts
  `poolmgrd`. A restart closes every `Events.Subscribe` stream, stops every
  reconciler mid-tick, and abandons any claim that is in its pre-lease hook.
- A pool spec names its hosts by string in `flintlock_hosts`. `CreatePool`
  does not check those names against the config. A typo surfaces later, as
  `ErrUnknownHost` from the reconciler, on every provision attempt.
- The config file must list at least one host. A manager with no hosts cannot
  start, so an operator cannot bring up the manager first and add hosts after.

PR #83 took the first step. It added a `HostAdmin` service with
`CordonHost`, `UncordonHost`, and `ListHosts`, a `hosts` table that holds
each host's name, address, and cordon state, and `poolmgrctl host
cordon|uncordon|list`. At startup `seedHosts` fills the table from the
config file and keeps the cordon state across restarts. `PickHost` skips
cordoned hosts, and `ReservePlacement` refuses a placement on a host that was
cordoned after `PickHost` chose it. `HostStatus.vm_count` counts every VM
record on the host in any phase, plus reserved placements, so an operator
knows when a cordoned host is empty.

What #83 does not do is let the set of hosts change. The table records what
the config file said. It holds no TLS material, so it cannot be the source
the client pool dials from. Adding or removing a host still means a restart.
This decision extends #83's service and table so that they can.

Issue #96 (SPIFFE identity for flintlock) changes where TLS material comes
from. Issues #69 and #102 (certificate reload) change when it is read. This
decision must not block any of them.

## Decision

Extend `HostAdmin` with `AddHost`, `UpdateHost`, `RemoveHost`, and `GetHost`.
Extend the `hosts` table with the TLS material. The store becomes the only
source of truth for the set of hosts, and the client pool dials from it. The
config file no longer lists hosts at all.

### API

Additions to `hostadmin.proto`:

```proto
service HostAdmin {
  // From PR #83.
  rpc CordonHost(CordonHostRequest) returns (Host);
  rpc UncordonHost(UncordonHostRequest) returns (Host);
  rpc ListHosts(ListHostsRequest) returns (ListHostsResponse);

  // New.
  rpc AddHost(AddHostRequest) returns (Host);
  rpc UpdateHost(UpdateHostRequest) returns (Host);
  rpc RemoveHost(RemoveHostRequest) returns (google.protobuf.Empty);
  rpc GetHost(GetHostRequest) returns (HostStatus);
}

message AddHostRequest {
  // Name, address, and tls are read. Cordon fields and timestamps are
  // ignored: a new host starts uncordoned.
  Host host = 1;
  // SkipValidation adds the host without dialing it. Use it to register a
  // host before it is reachable.
  bool skip_validation = 2;
}

message UpdateHostRequest {
  // Host is matched by host.name and carries the new address and tls. Cordon
  // fields are ignored; CordonHost and UncordonHost own them.
  Host host = 1;
  bool skip_validation = 2;
}

message RemoveHostRequest {
  string name = 1;
}

message GetHostRequest {
  string name = 1;
}
```

Additions to the `Host` message in `types.proto` and the `HostStatus`
message in `hostadmin.proto`:

```proto
// HostTLS carries what config.TLSConfig carried for a host. File paths are
// resolved on the machine that runs poolmgrd, not on the caller's machine.
message HostTLS {
  bool insecure = 1;
  string ca_file = 2;
  string cert_file = 3;
  string key_file = 4;
}

message Host {
  // Fields 1 to 6 as in PR #83: name, address, cordoned, cordoned_reason,
  // cordoned_at, updated_at.
  HostTLS tls = 7;
}

message HostStatus {
  // As in PR #83.
  Host host = 1;
  int32 vm_count = 2;
  // FlintlockVersion is the version the last successful ServerInfo call
  // reported. Empty until the manager has checked the host.
  string flintlock_version = 3;
}
```

`GetHost` returns `HostStatus` rather than `Host` so that one call gives the
operator the same view a `ListHosts` row gives.

### Semantics

- `AddHost` validates name, address, and TLS with the rules
  `config.Validate` applies to a host today. It then dials the host and runs
  `flintlockclient.CheckVersion`. If the host is unreachable or older than
  `MinFlintlockVersion`, `AddHost` fails with `FAILED_PRECONDITION` and stores
  nothing. `skip_validation` skips the dial and the version check, not the
  spec rules. A duplicate name fails with `ALREADY_EXISTS`.
- `UpdateHost` replaces the address and TLS of an existing host. The manager
  closes the old connection and dials the new one. An RPC in flight on the
  old connection fails, and its caller retries as it does today for any
  transport error. The version cache entry for the host is cleared, so the
  next provision checks the version again. `UpdateHost` cannot rename a host
  and does not touch its cordon state.
- `RemoveHost` refuses with `FAILED_PRECONDITION` while any pool spec names
  the host in `flintlock_hosts`, or while `vm_count` is above zero. Because
  `vm_count` includes reserved placements, a VM that is mid-creation cannot
  slip through. The operator's path is: `CordonHost`, drop the host from each
  pool spec, wait for `vm_count` to reach zero, `RemoveHost`. Cordoning stops
  new placements while the operator does the rest. The refusal keeps every VM
  record pointed at a host the manager can still reach, so `EnsureVMDeleted`
  never stalls on `ErrUnknownHost`.
- `CreatePool` and `UpdatePool` reject a `flintlock_hosts` entry that names
  no known host, with `INVALID_ARGUMENT`. Together with the `RemoveHost` rule
  this keeps pool specs and hosts consistent in both directions. `PickHost`
  keeps #83's cordon filter and needs no further change.
- `GetHost` and `ListHosts` read the store and the version cache. They do
  not probe the host. `vm_count` comes from #83's `CountVMsByHost`.
- The manager may run with zero hosts. It logs a warning at startup, and each
  pool's provision attempt fails with `ErrNoEligibleHost` until a host exists.

### Persistence

Extend #83's `hosts` table:

```sql
CREATE TABLE IF NOT EXISTS hosts (
    name            TEXT PRIMARY KEY,
    address         TEXT NOT NULL,
    cordoned        INTEGER NOT NULL DEFAULT 0,
    cordoned_reason TEXT,
    cordoned_at     INTEGER,
    updated_at      INTEGER NOT NULL,
    -- New.
    tls_insecure    INTEGER NOT NULL DEFAULT 0,
    ca_file         TEXT NOT NULL DEFAULT '',
    cert_file       TEXT NOT NULL DEFAULT '',
    key_file        TEXT NOT NULL DEFAULT ''
);
```

A database created since #83 merged already has the six-column table.
`schema.sql` is applied with `CREATE TABLE IF NOT EXISTS`, which cannot add
columns to it. The idempotent claims ADR proposes `PRAGMA user_version` and
a numbered migration list for the same reason. Whichever change lands second
uses the mechanism the first one adds.

The `Store` interface keeps #83's `GetHost`, `ListHosts`, `SetHostCordoned`,
`ReservePlacement`, `ReleasePlacement`, `ClearPlacements`, and
`CountVMsByHost`. It gains `CreateHost`, `UpdateHost`, and `DeleteHost`.
`UpsertHostIfMissing` goes: nothing seeds the table any more.
`ListCordonedHostNames` also goes, since `ListHosts` gives the host picker
both the cordoned and the registered hosts.

TLS material stays as file paths, as it is in the config file today. The
table holds no keys, and the API carries none. An operator who adds a host
over the API must first place the files on the `poolmgrd` machine. This is a
deliberate limit. Issue #96 replaces per-host files with a workload identity,
and inline PEM in the database would be a second thing for #96 to undo. The
paths are also what a per-handshake certificate reload (#102) would read, so
that work needs no change to this record.

### The config file

The `hosts` list leaves the config file. `config.HostConfig`, the host
`TLSConfig`, the "at least one host" rule, and #83's `seedHosts` all go with
it. What remains is the API server, the metrics address, and the sweeper
settings. A config file that still has a `hosts` key fails to load, with a
message that names `poolmgrctl host add`. There is no import path: the
project is pre-alpha, and an operator moves each host across with one CLI
call.

Pools have never had a config-file form. Hosts had one only because the
client pool needed something to dial before the API existed. With the store
as the source of truth, that reason is gone, and hosts follow pools.

Two things follow:

- `api_server` becomes required. A manager with no API can never learn a
  host, so `config.Validate` rejects a config without one, where today the
  daemon starts and logs a warning.
- A fresh manager has no hosts until something calls `AddHost`. A Kubernetes
  deployment needs a Job or an init step that runs `poolmgrctl host add`; a
  ConfigMap alone no longer suffices. This is the same shape as creating
  pools already is.

### Client pool

`flintlockclient.Pool` becomes mutable. It gains `Add`, `Update`, and
`Remove`, and guards its maps with a `sync.RWMutex`. `Client`, `ExecClient`,
`SSHProxyClient`, `Address`, and `Hosts` take the read lock. `New` no longer
takes a `*config.Config`. It takes the host list the store returns at
startup, so the same code path serves startup and `AddHost`.

### poolmgrctl

Add `poolmgrctl host add|update|remove|get <name>` beside #83's
`cordon <name>`, `uncordon <name>`, and `list`. `add` and `update` take
`--address`, `--flintlock-insecure`, `--flintlock-ca-file`,
`--flintlock-cert-file`, `--flintlock-key-file`, and `--skip-validation`,
and every command takes the usual `-o table|json`. The TLS flags carry a
`flintlock-` prefix because `--insecure`, `--ca-file`, `--cert-file`, and
`--key-file` are already poolmgrctl's root flags for its own connection to
`poolmgrd`. This is the change `AGENTS.md` requires for every API change.

### Auth and audit

`HostAdmin` sits behind the same server credentials as `PoolAdmin`. Any
caller who can create a pool can add a host. Host changes are logged at
`Info` with the host name, in the same style as the
`PoolAdmin` logging. They do not enter the events outbox: the `events` table
is keyed by pool, and a host belongs to no pool. Issue #67 (audit logging)
covers the durable record.

## Consequences

Positive:

- Operators add, change, and remove hosts without a restart. No stream
  drops, no abandoned claims.
- A bad host name in a pool spec fails at `CreatePool` with a clear message,
  not later in a reconciler log.
- A host that is down or too old is rejected when it is added, not on the
  first provision attempt.
- Cordon and remove compose: cordon first, remove when `vm_count` is zero.
  No second mechanism for taking a host out of service.
- One service, one table, and one CLI group for everything about hosts.
- One source of truth. No precedence rule between a file and the store, and
  no seeding code to keep them in step.
- Hosts and pools are managed the same way, which is what the Kubernetes
  operator (#46) and the Terraform provider (#71) will want.

Negative:

- The `hosts` table gains four columns, the `Store` interface gains three
  methods, and `flintlockclient.Pool` gains a lock. All callers of
  `flintlockclient.New` change signature.
- Every existing deployment must move its hosts to `poolmgrctl host add`
  when it upgrades. Until it does, its pools cannot provision.
- A fresh deployment needs one more step before it can provision, and the
  API server is no longer optional.
- TLS material still needs a file on the `poolmgrd` machine. A fully remote
  add is not possible until #96 lands.
- The design doc's "hosts are static config entries" paragraph and the
  README's config notes need updating.
- This or the idempotent claims change, whichever lands second, is the
  first to need a column migration.
- The fake flintlock double in `internal/e2etest` and the reconciler tests
  must build a `Pool` from a host list instead of a `config.Config`.

## Alternatives considered

- **A separate service for inventory, leaving #83's `HostAdmin` for cordon
  only.** Two services for one resource. Operators would look in two places
  and the CLI would need two command groups. Extending the existing service
  is less surface for the same result.
- **Watch the config file and reload it.** No new API, but it keeps every
  weakness of file-based inventory: remote operators cannot use it, and there
  is no place to validate a host or report its status. It also leaves the
  precedence question unanswered when the file and the running state differ.
- **Keep the config `hosts` list as a bootstrap list.** An earlier draft of
  this ADR did that: each host carried a `source` of config or API, startup
  upserted the file's hosts, a host dropped from the file passed to the
  API, and the API refused to remove a config-owned host. It preserved
  existing deployments and config-as-code for hosts. It also cost an enum, a
  column, three precedence rules, and a lesson for operators about which
  hosts leave through which door. Review judged that too much to keep for a
  pre-alpha project whose pools are already API-only.
- **Carry PEM bytes in the API and the store.** Allows a fully remote add. It
  puts private keys in SQLite and on the wire, and it conflicts with the
  direction of #96. Rejected for now.
- **Let `RemoveHost` force-remove a host with VMs on it.** Simpler for the
  operator in an emergency, but the VM records would then point at a host the
  manager cannot reach, and the deletion path would stall forever. Cordon
  already covers the "stop using this host now" case without that risk.
- **Validate `flintlock_hosts` only at provision time (as today).** Keeps
  `PoolAdmin` untouched, but then `RemoveHost` cannot tell whether a pool
  still depends on the host without scanning every spec, and `PickHost` must
  learn to skip unknown names as well as cordoned ones. Referential checks
  in both directions are fewer rules overall.

## Out of scope

- Cordoning itself. PR #83 decided that.
- SPIFFE identity and credential delivery to flintlock (#96).
- Reading TLS material per handshake instead of once at dial (#69, #102).
- Host events in the outbox and durable audit of host changes (#67).
- Automatic discovery of hosts from a cloud provider or service registry.
- Host capacity reporting beyond `vm_count`. Resource-aware scheduling is
  #18.
